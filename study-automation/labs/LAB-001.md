# LAB-001 — Kubernetes baseline health check

**Track:** Kubernetes | **Risk:** GREEN (read-only) | **Status:** Ready

## Objective
Identify the selected Kubernetes cluster, inspect all intended nodes and major system workloads, and explain cluster health with evidence. This is a guided inspection, **not an automated pass/fail health decision**.

## Preconditions
- `kubectl` is configured; select the intended non-production cluster context.
- Never use `sudo kubectl` or change contexts without verifying where you are.
- The reference architecture is a four-node lab; actual node roles must be determined from output.

## Commands
```bash
kubectl config current-context
kubectl get nodes -o wide
kubectl get pods -A
kubectl get deployments -A
kubectl get svc -A
kubectl get storageclass
kubectl get events -A --sort-by=.lastTimestamp
```
Optional scripted capture: `bash study-automation/scripts/lab001_collect.sh` and then `python3 study-automation/scripts/lab001_validate.py <output-directory>`.

## Validation
- Verify selected context corresponds to your intended lab.
- Identify all expected nodes and their roles/Ready states.
- Count non-Running / non-Completed Pods and explain any exceptions.
- Identify deployed apps, Services and StorageClasses.
- Distinguish historic warning Events from active incidents.
- Validate API collection with the local Python validator; validator passing means commands succeeded, **not** the cluster is healthy.
- Explain how scheduler, kubelet and container runtime participated in creating one running Pod.

## Human review questions
1. Which nodes are control-plane nodes? How did you determine that?
2. Are four nodes visible? If not, what is your next read-only diagnostic?
3. What is the most urgent evidence-backed issue, if any?
4. What commands would you run next? Which would require explicit approval?

## Approval checkpoints
- Inspection commands: GREEN — no change approval required.
- Any corrective action, installation or restart: stop, write impact + rollback, and obtain explicit human approval before proceeding.

## Completion evidence
Sanitized command outputs or a concise report, mentor's Pass/Needs Work decision, and a linked issue or PR when recorded to GitHub.
